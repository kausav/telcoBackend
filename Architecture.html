INGENII — Telecom Agentic Synthetic Data Platform

Architecture and code-level walkthrough for the MVP scenario workflow: propose OR import-csv → confirm → generate. The design uses PydanticAI for constrained natural-language intent extraction, a standards-backed runtime registry for telecom semantics, a deterministic schema compiler, persisted HITL approval, and deterministic generation/validation.

MVP baseline: FastAPI · Pydantic / PydanticAI · Gemini · LangGraph · SQLite runtime stores · deterministic generators

1. Architecture principles

P0

LLM is not the telecom authority

Gemini extracts intent and resolves user language to candidate concepts. It does not create executable entities, fields, relationships, formulas, generators or enums.

P1

Standards define semantics

TM Forum, 3GPP and selectively MEF provide provenance-backed source semantics. INGENII normalizes these artifacts into a runtime registry.

P2

Compiler creates the schema

The scenario schema is built deterministically from the runtime registry plus approved generation-policy overlays. The LLM does not directly author the schema.

P3

HITL approves ambiguity

The human reviews the proposed schema and may apply safe edits. Unknown concepts and executable semantics remain blocked.

P4

Generation is deterministic

The approved contract is passed to the existing deterministic generation pipeline. Agentic scenarios do not get silently reinterpreted by later LLM stages.

P5

Every run is reproducible

Scenario metadata, schema, registry provenance, generation policy and validation results are persisted so a run can be audited and recreated.

Anti-hallucination rule: structured LLM output alone is not sufficient. Pydantic validates shape; registry resolution validates telecom vocabulary; deterministic compilation validates executable semantics.

2. Industry and Domain Selection

IndustryType = model-family selector

industryType is the authoritative industry selector. For the current release, Telecommunications, Telecom and their normalized forms select the telecom model family. Unsupported industries are rejected before proposal compilation.

Domain = variable selector

domain is the authoritative business-domain selector inside the chosen industry. It is passed to the standards-backed runtime registry as the deterministic search query used to retrieve suitable entities and variables.

flowchart LR I[industryType] --> N[Normalize Industry] N --> T[Telecom Model Family] D[domain] --> R[Deterministic Domain Search] T --> R R --> C[TM Forum / 3GPP / MEF Runtime Registry] C --> S[Registry-backed entities, attributes, relationships] S --> SC[Deterministic Schema Compiler] SC --> H[HITL Confirmation] H --> G[Deterministic Generation]
Anti-hallucination boundary: Gemini receives a domain-scoped approved catalog and returns intent only. The LLM never selects an authoritative standard, creates a field, creates a relationship, or changes a generator. Industry selection is backend-controlled; domain selection is registry-controlled.

4. Public API contract

The scenario workflow exposes four APIs. Clients may choose either the agentic JSON proposal path or the explicit CSV definition path; both converge on the same HITL confirmation and generation APIs. Liveness and health endpoints remain operational endpoints.

3.1 POST /scenario/propose

The request body is the business-facing JSON contract. The backend derives technical schema details, resolves concepts against the TM Forum / 3GPP / MEF runtime registry, and deterministically builds an approved-registry schema containing at least 20 variables before HITL confirmation.

{
  "scenarioId": "LB-01",
  "scenarioType": "Normal",
  "industryType": "Telecommunications",
  "domain": "Low Balance & Top-up",
  "businessScenario": "Generate a high-fidelity synthetic dataset to model subscriber recharge behavior, analyze top-up trigger sensitivity, and evaluate proactive retention interventions without exposing sensitive customer PII.",
  "typeOfData": "transactional",
  "country": "IN",
  "entityKey": "subscriber_id",
  "useCase": "prepaid"
}
Response contract: ScenarioImportResponse is shared with CSV import and exposes requested_scenario_id, draft_id, scenario_id, variables, field_order, typeOfData, and entityKey. Agentic proposals must contain at least 20 distinct registry-backed variables.

3.2 POST /scenario/import-csv

This path remains available for clients that already have a complete variable-level CSV definition. It accepts the same scenario metadata as before as multipart form fields plus a UTF-8 CSV file, parses and normalizes the CSV deterministically, and creates a non-agentic draft.

multipart/form-data
  file: definition.csv
  scenarioId: PREPAID-CSV-01
  domain: telecom
  typeOfData: transactional
  industryType: telecom
  country: IN
  businessScenario: Prepaid recharge and usage
  scenarioType: csv
  useCase: prepaid
  label: Prepaid CSV
  entityKey: subscriber_id

The parser supports the existing client CSV conventions for types, generators, dependency aliases, timestamp formats, numeric buckets, weights, precision, currency and related deterministic parameters. The resulting response is the same ScenarioImportResponse used by /scenario/propose, including requested_scenario_id.

3.3 POST /scenario/confirm

This is the only HITL action API. It accepts draft_id, optional safe field edits, deletions, and feedback.

{
  "draft_id": "draft-...",
  "add": [],
  "edit": [
    {"name": "recharge_amount", "changes": {"description": "Recharge amount in INR"}}
  ],
  "delete": [],
  "feedback": "Use realistic Indian prepaid behavior"
}

For agentic drafts, confirmation rejects unknown fields and executable semantic changes. Generator names, formulas, dependency contracts and new parameters cannot be invented through HITL.

3.4 POST /scenario/generate

{
  "scenario": "PREPAID-01",
  "draftId": "draft-...",
  "count": 1000,
  "recordsPerUser": 10
}

An agentic scenario is resolved from the confirmed scenario record and executed from its persisted contract. The API is deliberately separated from schema proposal so generation cannot silently change the approved semantics.

Follow-up conversation

The proposal request intentionally contains only business-facing fields. The backend derives conversation context from scenarioId, loads prior messages before interpretation, and keeps the four-API contract unchanged. Follow-up instructions can therefore reuse the same scenarioId without exposing technical chat/session fields in the request body.

Important boundary: even if the model names an unsupported concept, the proposal is not executable. Registry resolution records the concept as unresolved and /scenario/confirm refuses promotion until the issue is resolved.

5. Standards-backed runtime registry

The application contains no hard-coded Python telecom catalog; core/telecom_registry.py is an implementation of a read-only runtime registry over SQLite; the source material lives under versioned normalized artifacts and generation-policy overlays.

flowchart LR TMF[TM Forum artifacts] --> N[Normalized JSON artifacts] GPP[3GPP artifacts] --> N MEF[MEF artifacts when applicable] --> N N --> B[RegistryBuilder] GP[INGENII generation profiles] --> B B --> DB[(SQLite runtime registry)] DB --> API[TelecomRegistry] API --> C[SchemaCompiler]

5.2 Standards roles for telecom

TM Forum

Useful for CSP business/customer/product/service/account semantics. The current source model lineage is based on the Information Framework and relevant TM Forum APIs such as TMF654 Prepay Balance Management.

Information Framework · TMF654

3GPP

Useful for mobile-network and charging semantics, especially the 32.xxx management/charging family. Prepaid charging should use the relevant 3GPP release/specification rather than generic LLM assumptions.

3GPP portal

MEF

MEF is loaded as a first-class telecom standards pack. The MVP includes Subscriber Ethernet and Internet Access model subsets. It is selected automatically only when the requested concepts resolve to MEF-backed entities; it is not artificially injected into a mobile-prepaid schema where it is not semantically relevant.

MEF Information & Data Models · MEF 139

Deterministic standard applicability: the platform does not ask Gemini to choose TM Forum, 3GPP or MEF. It resolves the requested concepts first, then groups source provenance from the runtime registry. A prepaid request may therefore resolve primarily to TM Forum + 3GPP, while a connectivity request can resolve to MEF + TM Forum, with 3GPP added only when mobile charging/network semantics are actually requested.

6. HITL / confirmation workflow

flowchart LR D[Draft schema] --> V[Deterministic validation] V --> H[Human review] H -->|Approve| C[Confirmed scenario] H -->|Safe edit| V2[Revalidate edit] V2 --> H H -->|Reject| X[Rejected / discarded] V -->|Unresolved concept| Q[Resolve before confirm] Q --> H

Allowed HITL changes

For agentic drafts, HITL can make presentation-level or safe contract-level changes that remain within the approved registry-backed definition: descriptions, nullability where allowed, existing parameter values, and field deletion where dependencies and required fields remain valid.

Blocked HITL changes

new_entitynew_fieldnew_relationshipnew_generatornew_formulanew_enumunknown_parameter

A human can request a model extension, but that extension belongs in a new standards artifact or approved INGENII model extension, followed by registry rebuild and a new proposal.

7. Deterministic generation

The confirmed scenario is passed into the existing generation pipeline. The generator layer is responsible for record production; the LLM does not generate rows.

flowchart LR C[Confirmed Scenario] --> P[core/pipeline.py] P --> LG[LangGraph] LG --> O[Orchestrator] O --> S[SchemaAgent / rules] S --> D[DataGenerationAgent] D --> X[Dependency-aware generation] X --> T[Transactional grouping or flat aggregate] T --> Q[QA / Repair] Q --> R[GenerateResponse]

Agentic scenario exception

For confirmed agentic scenarios, the orchestrator and schema stage use the persisted registry-backed contract as authoritative input and skip additional semantic reinterpretation. This prevents a second LLM pass from mutating the approved schema.

The generation profile supplies deterministic behavior such as INR currency, Indian MSISDN generation, recharge denominations, subscriber status weights and relationship dependencies. Those are INGENII generation policies, not additional claims about the standards themselves.

8. Validation, reconciliation and repair

Quality is handled in multiple layers. A dataset is not considered valid merely because its columns match a Pydantic model.

LayerQuestion answered
Schema validationAre required fields present and typed correctly?
Registry validationDo entities, attributes and relationships exist in the approved model?
Reference validationDo foreign/reference values resolve to generated records?
Temporal validationDo causal timestamps occur in the correct order and within bounded delays?
Arithmetic validationDo derived values reconcile with their inputs?
Distribution validationDo generated records respect declared weights/buckets/precision?
RepairCan a bad record be deterministically corrected without changing the approved contract?
Example: if charge_timestamp is causally downstream of usage_timestamp, the validator checks charge_timestamp >= usage_timestamp. A failed row is repaired or rejected deterministically; the LLM is not permitted to change the relationship definition during generation.

9. Persistence and lifecycle

Conversation store

core/conversation_store.py persists user/assistant messages so proposal follow-ups can use chat context across requests and workers.

Scenario store

core/dynamic_scenarios.py persists drafts and confirmed scenarios. Runtime databases are ignored by Git and recreated on a clean environment.

Runtime registry

runtime_data/registry.db is mutable runtime state created automatically from the immutable resources under resources/telecom/. It is not source-of-truth model data and should live on a persistent deployment volume.

Cache invalidation

Scenario confirmation clears scenario-dependent cached artifacts so generation cannot accidentally use a stale schema.

Draft lifecycle

External LLM boundary

12. Production Deployment

Immutable resources

resources/telecom/ contains model artifacts and generation profiles shipped with the build. They are read-only inputs to registry construction.

Mutable runtime state

runtime_data/ is created automatically at startup for the registry, scenarios and conversations. Mount it on durable storage in production.

Configuration

Secrets and deployment-specific values are supplied through environment variables. CORS is explicit by default; production deployments should set approved origins.

Container

The supplied Dockerfile runs the service as a non-root user and copies only application source and immutable resources into the image.

MVP-to-production evolution

Now

Three standards packs (TM Forum, 3GPP, MEF), SQLite runtime registry, PydanticAI intent agent, four scenario APIs, persisted HITL through scenario confirmation, and deterministic generation.

Next

Replace curated MVP subsets with pinned official TM Forum, 3GPP and MEF machine-readable artifacts, preserve model/release lineage, and add graph search with formal evidence.

Later

Multi-domain standards packs, tenant-scoped registries, asynchronous generation jobs, richer provenance, large-scale data sinks and production observability.
