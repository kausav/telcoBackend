INGENII Telecom Agentic Synthetic Data Generator

High-level design of the currently implemented backend. The service combines FastAPI, MongoDB, machine-readable telecom standards, deterministic schema compilation, Gemini-based scenario intent interpretation, HITL approval, and deterministic record generation/validation.

API: FastAPI 2.8.0 Persistence: MongoDB LLM: Google Gemini Graph runtime: LangGraph for legacy/explicit CSV generation Agentic generation: deterministic fast path after confirmation
Primary source-of-truth rule: once a scenario is confirmed, its persisted executable variables and metadata are the generation contract. Agentic generation does not send the confirmed schema back to the LLM for reinterpretation.

1. Architecture Principles

Standards-first semantics

TM Forum, MEF and 3GPP machine-readable artifacts supply telecom entity/field meaning, constraints, relationships and provenance.

Policy is separate

telecom_official_generation_v2.json overlays sampling behavior; it is not treated as an official standards definition.

LLM is constrained

Gemini creates scenario intent. Executable schema fields are resolved and compiled against the trusted runtime registry.

HITL is the approval boundary

/scenario/confirm converts a proposal/import draft into the active persisted scenario used by generation.

Generation is deterministic after approval

Agentic scenarios use the confirmed schema directly. Legacy/CSV scenarios retain a LangGraph orchestrated path.

Validation is fail-closed

Type, dependency, formula, temporal and domain-specific checks run before records are accepted by the response contract.

LLM contract

Gemini is typed to ScenarioIntent. It can propose semantic variable ideas, requested entities/relationships, scenario metadata and related intent, but executable telecom fields are resolved by the backend.

Proposal cache

The agentic proposal cache key includes normalized request values, a deterministic hash of Mongo variable definitions and an official source-manifest fingerprint. This reduces stale proposal reuse after source changes.

Proposal cache

Bounded + TTL-backed. Keyed by normalized proposal input, Mongo definition fingerprint and standards-manifest fingerprint.

Compiled schema cache

Bounded process-local cache keyed by requested scenario identifier. Explicit invalidation occurs after confirmation.

Orchestrator cache

Used by the legacy LangGraph path to avoid repeated validation calls for the same scenario context.

Health model

Each request receives a bounded X-Request-ID. The same identifier is returned in the response header and is available to canonical error responses.

14. Security & Current Production Gaps

Current implementation gap: request models currently accept userId as a client-provided value and there is no authentication/authorization dependency protecting scenario or user-variable endpoints. The HLD documents this explicitly rather than presenting it as already implemented.
ConcernStatusCurrent behaviorRecommended hardening
AuthenticationGapNo auth middleware/dependency in server.py.Add OIDC/JWT or platform identity and enforce it at route boundaries.
Authorization / tenant isolationGapScenario/user ownership is not cryptographically tied to the caller.Derive user/tenant identity from authenticated claims; authorize every read/write.
HITL parameter semanticsHardeningExisting agentic edit validation blocks structural/provenance violations but should be strengthened with generator-specific semantic parameter validation.Validate min/max, weights, buckets, precision, references and date/range semantics before persistence.
Scenario concurrencyHardeningActive scenario is replaced on reconfirmation.Add immutable scenario revision + definition hash / optimistic concurrency.
Shared cache invalidationHardeningCaches are process-local.Use revision/hash-aware keys or shared cache for multi-worker deployment.
Generation scaleHardening/scenario/generate is synchronous.Introduce an asynchronous job path for very large datasets.
