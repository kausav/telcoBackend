3. CSV definition layer

Variable rows

Every row with an empty fields value is an entity/regular variable. record_type is optional and is not required to classify the CSV.

Dependencies

depends_on may reference any declared field. The importer validates references globally, so client rows do not have to be topologically ordered.

Generator parameters

params accepts legacy JSON or the client compact format such as prefix=SUB-;digits=7, min=50;max=1000, and delay_seconds=5-120.

Formulas

Formula variables use gen=formula and provide the expression in the formula column.

User history

Transactional variables are split by optional scope. Stable user/entity fields are generated once per entity; history fields are regenerated for each recent row.

Aggregational data

If every row has empty fields, the CSV is aggregational. The resulting records are one record per requested unit.

4. Transactional detection rule

CSV structure is authoritative: each row defines a variable. No event_type, sequence, or event grouping is used. Transactional generation returns users/entities with their most recent configured history rows.

For transactional input, the backend infers stable user/entity fields from the entity key and the first history timestamp field; no scope column is required.

5. Agent pipeline

Orchestrator Agent

Checks that the confirmed scenario exists and has usable CSV-defined variables. It may use cached validation or an LLM validation pass for business/industry coherence.

Schema Agent

Uses the confirmed CSV schema plus scenario context to derive machine-readable business rules, field constraints, conditional relationships, and formula rules. It does not replace the CSV variable definitions.

Data Generation Agent

Generates records algorithmically from the confirmed CSV schema, applies declared/rule-based constraints, validates types/ranges/formulas, and optionally performs the existing LLM QA audit.

The LangGraph pipeline is now three stages: orchestrator → schema → generation. Each stage can halt the pipeline when a fatal validation error is produced.

6. Data generation flow

  1. Resolve the confirmed scenario from SQLite.
  2. Load the exact variables and field order persisted from CSV.
  3. Infer the data type from CSV structure: any non-empty fields value means transactional; otherwise aggregational.
  4. Generate values using the generator specified by each CSV variable.
  5. Resolve declared dependencies in order.
  6. Apply Schema Agent machine-readable constraints and conditional relationships.
  7. Evaluate authoritative CSV formulas and repair mismatches deterministically.
  8. Run deterministic type, range, categorical, formula, and timestamp validation.
  9. Optionally run LLM QA according to QA_LLM_MODE.
  10. Return the validated records and validation report.

8. Persistence and caching

SQLite dynamic scenario store

Stores imported drafts and confirmed scenario metadata, variables, field order, entity key, and history settings. Confirmed data remains the source used by generation.

Compiled schema cache

Turns confirmed variables into fast user-context/history lookup structures for repeated generation calls. It is invalidated after scenario confirmation changes.

Runtime schema cache

Caches immutable runtime artifacts such as Schema Agent results. Cache misses recompute safely.
