Telco Agentic Synthetic Data Generator

A code-level architecture guide for the current telcoBackend-newBranch backend. This page explains how the FastAPI API, CSV schema compiler, SQLite persistence, LangGraph agents, deterministic generators, formula engine, transactional grouping, validation/repair, and caches fit together.

1. System overview

The current architecture is CSV-first. The imported CSV defines the actual variable catalog. The agents add semantic validation and business rules around that schema; they do not replace the CSV with a newly invented LLM schema.

flowchart LR A[Client / UI] --> B[FastAPI: server.py] B --> C[CSV Parser: core/csv_scenario.py] C --> D[(SQLite: core/dynamic_scenarios.py)] B -->|confirm| D D --> E[WorkflowState: core/state.py] E --> F[LangGraph: core/pipeline.py] F --> G[OrchestratorAgent] G --> H[SchemaAgent] H --> I[DataGenerationAgent] I --> J[Validated Records] J --> B H -. LLM reasoning .-> K[Gemini Client: core/llm_client.py] I -. optional LLM QA .-> K I --> L[Compiled Scenario Cache] L --> I D --> L
Source of truth

Confirmed CSV schema

Variable names, datatypes, generators, parameters, dependencies, formulas, descriptions, and related metadata originate in the imported definition CSV and are persisted into the confirmed scenario.

Agentic

LLM as semantic layer

Gemini is used to validate/interpret business context and derive machine-readable rules. This is intentionally different from letting the LLM invent the field catalog.

Deterministic

Python generation engine

Actual record values are primarily produced by explicit generator functions and dependency-aware execution in data_generation_agent.py.

Stateful

SQLite + caches

Drafts, confirmed scenarios, feedback, compiled schemas, and runtime artifacts provide persistence and reduce repeated work across requests.

  -H "X-Request-ID: demo-import-001" \
  -F "file=@samples/definition_sample.csv" \
  -F "scenarioId=LB-01" \
  -F "domain=Recharge" \

Importer behavior: the CSV is decoded, parsed by parse_definition_csv(), and normalized into variables plus field_order. For transactional scenarios, entityKey is either matched case-insensitively to a supplied name or inferred from preferred identifiers such as subscriber_id, customer_id, account_id, user_id, and entity_id.

2.1.2 POST /scenario/confirm

Content-Type: application/json. This is the schema-edit and commit boundary: the temporary draft becomes the confirmed scenario used by generation.

{
  "draft_id": "DR-abc123",
  "add": [
    {
      "name": "customer_tier",
      "dtype": "categorical",
      "gen": "choice",
      "params": {"values": ["prepaid", "postpaid"]}
    }
  ],
  "edit": [
    {
      "name": "recharge_amount",
      "changes": {"params": {"min": 10, "max": 5000}}
    }
  ],
  "delete": ["obsolete_field"],
  "feedback": "Prefer INR amounts and Indian telecom context"
}

The route applies operations in this order: delete → edit → add. It then rebuilds field_order, re-evaluates the transactional entity_key, persists metadata + variables, invalidates the compiled/runtime caches, optionally stores feedback, and removes the draft with pop_draft().

3. CSV parsing and schema compilation

core/csv_scenario.py is effectively a domain-specific parser/compiler. It transforms loosely formatted CSV rows into a normalized internal variable representation that the rest of the application can execute.

flowchart TD A[Raw CSV text] --> B[infer_type_of_data] A --> C[parse_definition_csv] C --> D[Parse scalar / list values] D --> E[Parse params: JSON or compact syntax] E --> F[Normalize dtype] F --> G[Normalize generator] G --> H[Normalize formula] H --> I[Resolve dependency aliases] I --> J[Align id_mirror sources] J --> K[Merge / validate duplicate variables] K --> L[Global dependency validation] L --> M[field_order + variables] B --> M

Parameter formats

The parser supports structured JSON as well as compact forms such as prefix=SUB-;digits=7, min=50;max=1000, and range-like values.

Generator normalization

Aliases and context-sensitive generator forms are normalized before execution, so the runtime sees a consistent generator contract.

Formula normalization

_coerce_formula_text() converts CSV-friendly expression syntax into executable expressions that the deterministic formula engine can evaluate later.

Dependency validation

The importer resolves references against the full field set, allowing rows to be supplied in a non-topological order while still rejecting unknown dependencies.

Type-of-data inference

infer_type_of_data() uses CSV structure. Non-empty fields values indicate transactional/history-style input; otherwise the scenario is treated as aggregational.

Duplicate and legacy handling

The parser contains compatibility logic for duplicate variables, generator aliases, legacy formats, and id_mirror source alignment.

Important: the parser is not a thin CSV reader. It performs normalization and semantic validation before anything reaches the agents. This is why debugging an “LLM problem” should often start by inspecting the parsed variable object first.

Representative normalized variable shape

{
  "name": "subscriber_id",
  "dtype": "string",
  "gen": "prefixed_int",
  "params": {"prefix": "SUB-", "digits": 7},
  "depends_on": [],
  "formula": "",
  "nullable": false,
  "description": "Stable subscriber identifier"
}

4. LangGraph pipeline and agent responsibilities

core/pipeline.py builds a three-node LangGraph. Each node is wrapped so the graph can stop when the shared WorkflowState contains fatal errors.

flowchart LR S[WorkflowState] --> O[1. OrchestratorAgent] O -->|ok| SC[2. SchemaAgent] O -->|fatal errors| X[Stop] SC -->|rules| DG[3. DataGenerationAgent] SC -->|fatal errors| X DG --> R[final_records + validation_report] DG --> E[errors / record_errors] O -. reads .-> DB[(SQLite scenario)] SC -. context + variables .-> LLM[Gemini] DG -. optional QA .-> LLM

OrchestratorAgent

Purpose: gate the request before expensive downstream work.

  • Checks that the confirmed scenario exists.
  • Checks that the scenario has usable CSV-defined variables.
  • May use cached validation or an LLM validation pass for scenario/business coherence.
  • Produces state/errors that can halt the graph.

SchemaAgent

Purpose: translate business context into machine-readable rules around the confirmed schema.

  • Receives industry, country, business scenario, use case, outcome, and variables.
  • Derives constraints, conditional relationships, semantic rules, and formula-related rules.
  • Returns structured rules rather than generating the final records.

DataGenerationAgent

Purpose: execute the actual schema deterministically.

It contains the generic generator registry, dependency ordering, record construction, transactional history generation, formula evaluation, deterministic validation/repair, and optional LLM QA.

Boundary that matters: the LLM is upstream of deterministic generation. If generated values violate an explicit CSV formula or parameter constraint, the deterministic layer has authority to repair them. That makes the final result more reproducible than an LLM-only generator.

5. Generation engine: dependency-aware execution

The core record builder is _generate_record(). It does not simply loop over the CSV rows. It first determines a dependency-safe execution order.

flowchart TD A[Variables] --> B[Extract explicit depends_on] A --> C[Extract formula dependencies] B --> D[Build dependency graph] C --> D D --> E{Cycle?} E -->|yes| F[Raise / report dependency error] E -->|no| G[Topological order] G --> H[Generate field value] H --> I[Apply generation constraints] I --> J[Apply conditional rules / scenario semantics] J --> K[Evaluate formulas] K --> L[Record]

Generator registry

Identity / telecom

prefixed_int, prefixed_uuid, tx_id, id_mirror, e164_phone

Simple distributions

constant, weighted_choice, uniform, lognormal, lognormal_int, beta

Bounded / segment aware

segment_range, uniform_bounded

Temporal

recent_datetime, ts_offset, ts_add_field, date_offset

Derived

formula plus rule-based formula sources and dependency extraction.

Why dependency order matters

Example:

subscriber_id       -> generated first
segment              -> generated second
monthly_spend       -> generated from segment
recharge_amount     -> generated from monthly_spend
balance_after       -> formula(monthly_spend, recharge_amount)

Even if the CSV places balance_after above the other fields, the dependency graph can place it last.

6. Transactional vs aggregational generation

core/compiled_schema.py compiles confirmed scenarios into two logical field sets: stable entity/user context and history fields. The transactional generator uses that compiled representation.

flowchart TD A[Confirmed variables] --> B[compile_scenario] B --> C[infer_history_field_sets] C --> D[Stable entity fields] C --> E[History fields] D --> F[Generate entity once] E --> G[Generate N history rows per entity] F --> H[Combine entity + history] G --> H H --> I[Latest configured response window] J[Aggregational scenario] --> K[Generate requested records directly]
AspectTransactionalAggregational
PurposeRepresent entities/users plus recent historical events/measurements.Represent independent records at the requested grain.
Stable fieldsGenerated once per entity/user.Generated per record.
History fieldsRegenerated for each history row.Not split into a separate history phase.
DetectionBased on CSV structure and transactional metadata/field grouping.Empty fields structure indicates the aggregational path.
Key implementationcompile_scenario(), infer_history_field_sets(), _transactional_records()_generate_record() repeated for requested count.
Timestamp boundary: the compiled-schema logic uses the first appropriate history timestamp field as a practical boundary when separating stable entity context from historical fields. That makes timestamp naming/ordering a meaningful part of transactional CSV design.

7. Persistence, cache layers, and invalidation

flowchart TB API[FastAPI requests] --> DB[(SQLite)] DB --> D[Draft scenarios] DB --> C[Confirmed scenarios] DB --> F[Feedback history] C --> CS[Compiled schema cache] C --> RC[Runtime/schema cache] CS --> GEN[Data generation] RC --> AG[Agent orchestration] CONF[Scenario confirmation] --> INV[Invalidate scenario caches] INV --> CS INV --> RC

SQLite: dynamic_scenarios.py

Initializes/migrates the DB, stores drafts, confirms scenarios, resolves metadata/variables/type/entity key, and stores feedback history.

Compiled schema cache

compile_scenario() produces an immutable compiled representation optimized for transactional lookup and repeated generation calls.

Runtime cache

core/runtime_cache.py keeps process-local runtime artifacts such as schema/agent results so repeated calls can avoid recomputation.

Invalidation

Scenario confirmation explicitly clears scenario-dependent cached artifacts so generated data is not based on an older schema.

8. Validation and repair: why generation is more than random sampling

The QA path in data_generation_agent.py is a deterministic repair loop. The system can fix values instead of merely rejecting an entire record.

flowchart LR A[Generated record] --> B[Fill missing fields] B --> C[Coerce datatypes] C --> D[Check declared params] D --> E[Check ranges / categories] E --> F[Check timestamps] F --> G[Evaluate authoritative formulas] G --> H[Apply conditional / semantic rules] H --> I{Valid?} I -->|yes| J[Final record] I -->|no, repairable| B I -->|no, fatal| K[Record error / pipeline error]

Deterministic formula safety

_safe_formula() evaluates normalized expressions through a restricted AST rather than calling unrestricted eval(). The formula layer also extracts dependencies so formulas can participate in generation ordering.

Authority order: explicit CSV formulas and declared generator constraints are the strongest constraints; Schema Agent rules add business semantics; optional LLM QA can audit the output but does not replace the deterministic validation path.

10. Design rules and useful debugging checkpoints

Rule 1 — CSV before LLM

When a generated field is wrong, first inspect the normalized variable produced by parse_definition_csv(). A malformed generator, dtype, params, dependency, or formula can propagate all the way into generation.

Rule 2 — dependencies are executable semantics

depends_on and formula references are not documentation only; they affect generation order and can create cycle failures.

Rule 3 — transactional shape matters

The split between stable and history fields influences output structure. Timestamp placement and entity-key behavior can therefore change how a scenario is generated.

Rule 4 — LLM rules are advisory relative to explicit CSV contracts

Business semantics can be enriched by Gemini, but explicit CSV formulas and generator parameters remain deterministic constraints.

Rule 5 — cache state matters

When changing a confirmed scenario, stale compiled or runtime artifacts can cause confusing “old behavior.” The confirmation path explicitly invalidates the relevant caches for this reason.

Rule 6 — QA can mask generator defects

Because validation repairs values, the final output can look correct even when an earlier generator/rule is producing the wrong initial value. Debugging may require inspecting the pre-repair path.

Typical debugging sequence

1. Inspect request payload / uploaded CSV
2. Inspect parse_definition_csv() output
3. Inspect confirmed scenario in SQLite
4. Inspect WorkflowState entering the graph
5. Inspect SchemaAgent rules
6. Inspect dependency order in _generate_record()
7. Inspect raw generated values before _validate_record()
8. Inspect repairs + validation_report
9. Inspect final response shaping in server.py
Architecture in one sentence: FastAPI accepts a CSV-defined schema, SQLite persists the normalized scenario, LangGraph coordinates semantic validation and rule derivation, deterministic Python generators execute the schema in dependency order, and a repair/validation layer produces the final records.
