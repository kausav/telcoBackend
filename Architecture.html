Ingenii Backend — Agentic Architecture Overview

1. Purpose

This service generates synthetic telecom "low-balance / top-up" event data for testing, analytics, and ML training pipelines. Instead of a fixed template, it uses a multi-agent pipeline (LLM + deterministic code) so that:

  • Business rules and validation logic are derived by an LLM from a plain-English scenario description (auditable, not hardcoded).
  • Bulk record generation itself is fast and deterministic (no LLM latency/cost per record).
  • New scenarios can be created on demand through human–LLM collaboration, without writing new generator code.

What happens: A request enters through the FastAPI layer and is converted into a shared WorkflowState. The pipeline validation service checks that the scenario is coherent before expensive generation begins. The Rules Agent turns the scenario into executable constraints, the Data Generator creates records using deterministic Python generators, and QA validates the result. Gemini is used only where semantic reasoning is useful; the core record generation remains deterministic.

3. Agentic Architecture Deep Dive

Four Agents Total (Three Runtime Pipeline Agents + One On-Demand Scenario Designer)

  • Rules Agent
  • Data Generator Agent
  • QA & Validation Agent
  • Scenario Designer Agent (on-demand; used by scenario proposal/confirmation flow, not by the generation pipeline)

Not counted as agents (components/layers, not agents):

  • WorkflowState (Pydantic object threaded through the pipeline)
  • SQLite dynamic-scenario store (drafts / confirmed / feedback tables)
  • GeminiClient wrapper (core/llm_client.py)

Why this order: Each stage consumes the decisions made by the previous stage. This prevents the generator from inventing its own interpretation of the scenario and gives QA the rules and schema needed to check whether generated values are actually valid.

Data Generator internal flow

flowchart TB V["Confirmed or configured variable catalog"] --> O["Apply scenario overrides
Use confirmed user values"] O --> L["Walk variables in declared order"] L --> D["Generator dispatch table
uniform / lognormal / beta / choices / formula / timestamps"] D --> R["Build record incrementally"] R --> F["Formula fields read prior values
and preserve dependencies"] F --> OUT["Validated candidate record"]

What the generator does: It reads the effective variable schema, applies data-driven scenario overrides, and generates variables in dependency order. Formula fields can use values already produced in the same record. Generator behavior is selected from a generic dispatch table; there are no scenario-ID-specific generator functions such as LB-01/LB-02 handlers. Scenario and industry behavior comes from the confirmed schema, rules, formulas, profiles, and edge-case definitions rather than hard-coded scenario implementations.

3.1 Pipeline Validation Service

Role: Gatekeeper service — validates the scenario request before generation work happens. This is deterministic application orchestration plus one semantic LLM validation call; it is not an agent and does not consume an agent slot.

Inputs: confirmed scenario context, industry, country, data type, and requested record count.
Outputs: Pass/fail decision and execution notes. The pipeline halts immediately on failure.

  • Checks scenario exists (static config/scenarios.py + SQLite dynamic store)
  • Asks Gemini (temperature 0.1) to sanity-check the scenario and produce execution notes
  • Appends errors to state.errors and stops the pipeline on rejection

3.2 Rules Agent

Role: Derives the business rules and field constraints that generated records must satisfy — becomes the shared contract used later by QA.

Inputs: scenario metadata + variable definitions.
Outputs: business_rules[], field_constraints{}, cross_field_rules[] (temperature 0.1).

  • Summarizes every variable for the LLM
  • Produces a complete rules document covering all variables
  • Stores rules in shared state (state.rules) for the QA Agent to consume

3.3 Data Generator Agent

Role: The actual generation engine — makes zero LLM calls per record.

Inputs: variable catalog (static or dynamic) + scenario overrides.
Outputs: raw_records[].

  • Resolves each variable via a dispatch table (uniform, lognormal, beta, weighted_choice, formula, timestamp helpers, etc.)
  • Generates fields in dependency order so later fields can read earlier ones already written (e.g. account_id mirrors subscriber_id)
  • Sandboxes formula-type fields via eval() with __builtins__ disabled

3.4 QA & Validation Agent

Role: Two-layer validation — deterministic checks first, then LLM semantic audit.

Inputs: raw_records[], business rules from the Rules Agent.
Outputs: final_records[], validation_report{}.

  • Recomputes balance_after, trims to official field order, default-fills any null field (0 / "" / False)
  • Sends records in chunks of 50 to Gemini (temperature 0.1) for semantic review
  • Recovers any record the LLM drops (default-filled and re-added) so output count matches the request
  • Passes a chunk through unmodified (and logs an error) if its LLM call fails, rather than crashing the whole run

3.5 Scenario Designer Agent (on-demand)

Role: Invents a brand-new scenario's full variable catalog from a plain-English business description, via /scenario/propose + /scenario/confirm.

Inputs: industryType, domain, businessScenario, optional businessResponse/expectedOutcome, plus feedback history.
Outputs: 15–35 variable catalog in the same generator vocabulary the Data Generator Agent already understands.

  • Normalizes field name synonyms to a canonical glossary (e.g. customer_id → subscriber_id)
  • Force-includes 3 mandatory cross-scenario fields
  • Retries once if too few variables are returned (temperature 0.3)
  • Persists confirmed scenarios into the SQLite store shared across all Cloud Run / Uvicorn worker processes
flowchart TB U["User scenario input"] --> P["POST /scenario/propose
Create variable and edge-case draft"] P --> D["Draft stored in SQLite"] D --> C["POST /scenario/confirm
Add / edit / delete variables and edge cases"] C --> V["Validate effective schema and edge conditions"] V --> S["Confirmed scenario stored"] S --> G["POST /scenario/generate"] G --> PIPE["Generation + validation pipeline"] C -.-> FB["Feedback stored in SQLite"] FB -.-> P

Scenario lifecycle: /scenario/propose creates a draft schema. Confirmation is the point where user edits become authoritative, so the effective variable schema and edge-case definitions are validated before storage. Generation then consumes the confirmed scenario instead of silently using an older draft.

4. Validation Approach (actual — no separate "Progressive Validation Gates")

The current codebase does not implement separate named validation gate components. Validation is folded into two places:

  • Design-time validation → Rules Agent (derives constraints before generation)
  • Post-generation validation → QA Agent (algorithmic checks + LLM semantic audit, in chunks of 50)

6. Orchestration State Management

Instead of a Firestore-backed GenerationState, the real implementation uses a single in-memory Pydantic model (core/state.py) passed by reference through each agent call:

WorkflowState
├── scenario            (e.g. "LB-01")
├── count                (records requested)
├── batch_size           (QA chunk size, default 50)
├── rules                (populated by Rules Agent)
├── raw_records          (populated by Data Generator Agent)
├── final_records        (populated by QA Agent)
├── validation_report    (populated by QA Agent)
├── errors               (any agent can append; halts the pipeline)
└── field_order          (populated by Data Generator Agent)

Persistence model (actual): SQLite (WAL mode) — data/dynamic_scenarios.db (drafts / confirmed / feedback tables). There is no Firestore, BigQuery, or Cloud Storage integration. WorkflowState itself is not persisted between runs.

7. Agent Routing Logic and Error Recovery (actual)

flowchart TB START["Pipeline starts"] --> O["Pipeline validation service
Reject incoherent scenario early"] O -->|reject| STOP["Return structured error"] O -->|accept| R["Rules Agent
Build constraints"] R --> G["Generator
Generate records"] G --> E["Edge-case solver
Construct records when random data is insufficient"] E --> Q["QA Agent
Re-evaluate complete records"] Q -->|valid| F["Return final records"] Q -->|invalid| ERR["Return validation error
without falsely marking the record valid"]

Error handling: Failures are stopped at the stage that can explain them. Edge-case generation is not a variable-specific bypass: the solver constructs candidates from the declared condition, then the complete condition is evaluated again. QA is the final authority for whether an edge-case flag is truthful.

  • Pipeline validation rejection → generation stages do not run
  • QA per-chunk LLM failure → chunk is logged as an error and passed through as-is, not retried or routed back
  • No root-cause-classified routing back to Rules/Data Generator Agent on QA failure exists today

8. Deployment Topology (actual — GCP)

Build and test"] CI --> AR["Artifact Registry

Run FastAPI service"] SM["Secret Manager

Deployment action: A source change is built into a container image, stored in Artifact Registry, and deployed to Cloud Run. The Gemini credential is injected through Secret Manager rather than committed to source code. API consumers then call the deployed FastAPI service.

  • Container listens on $PORT (Cloud Run convention, default 8080)
  • Gemini key injected from Secret Manager at deploy time — never baked into the image or committed
  • Known limitation: Cloud Run's filesystem is ephemeral and not shared across instances — the SQLite dynamic-scenario store does not persist reliably across revisions/scale-out there

9. Final Architecture Principles (actual, current implementation)

  • Direct client input flow: HTTP API request feeds into run_generation_pipeline() — no separate Domain Knowledge Layer
  • Generation does not wait on QA approval — generation and validation are sequential stages, not a gated loop
  • Deterministic generation, hybrid validation
  • No contract objects / versioning — WorkflowState is the only hand-off object, valid for one run
  • No forward/reverse traceability implementation exists today
  • Reproducibility is partial — no random seed capture or generation manifest is persisted

11. API Reference (server.py)

API order: POST /scenario/propose → POST /scenario/import-csv → POST /scenario/confirm → POST /scenario/generate. There is no backend /scenario/download-csv; CSV export is handled by the frontend.

All request/response fields below are taken directly from the Pydantic models in server.py. "Required" means the field has no default (must be supplied); everything else is optional and falls back to its default (often null / empty list) if omitted or sent as blank/"string"/null placeholder text.

POST /scenario/generate — API 4

Purpose: Run the generation pipeline (Rules → Generator → QA) after pipeline-level scenario validation for a confirmed scenario and return generated records.

Request body (GenerateRequest):

Field Type Required Description

*Either scenario or draftId must be supplied (enforced at runtime, not by the schema) — a 400 is returned if both are missing.

validation_report object QA agent's validation summary

12. Edge-Case Data Model and Validation

Edge cases are first-class scenario definitions and are handled generically across industries and data types.

FieldPurpose
edgeCaseVariablesVariables and constraints defining an edge condition; it can be empty when no edge case is configured.
edgeCasePercentageRequested fraction of generated records that should satisfy configured edge conditions. Valid range is 0 through 1; when no edge-case variables exist, the effective value is 0.
isEdgeCaseDataTrue only when the final generated record actually satisfies a configured edge condition.
  • Generic constraint solving: handles comparisons, field-to-field relationships, numeric coercion, boolean semantics, and compound logical expressions.
  • Confirmation: validates the effective schema and edge conditions before a scenario is confirmed.
  • Generation: computes the target edge-case count from total count and percentage and constructs candidates when random records do not naturally satisfy the condition.
  • Truthful classification: the flag is derived from evaluating final values, not from merely selecting a record as an edge-case candidate.
  • Formula consistency: dependent values are recalculated after edge-case assignments.
  • Transactional and aggregational: the same generic edge-case principles apply to both data types.

13. Frontend Data Export

The backend no longer exposes a CSV download API and does not persist generated datasets under a generated_data directory. The /scenario/generate response remains the source of the generated data, and the frontend is responsible for converting the received records into CSV when the user chooses to download them.

flowchart LR G["POST /scenario/generate"] --> R["Generated JSON response"] R --> T{"Data type"} T -->|transactional| TR["records[]
entity -> events[] -> records[]"] T -->|aggregational| AG["records[]
row objects"] TR --> X["Frontend flattening
One event record = one CSV row"] AG --> X X --> E["Dynamic column union + CSV escaping"] E --> F["Frontend download
proposed_scenario_id_records.csv"]

Frontend export: Transactional responses contain entity-level data and nested event records, so the frontend expands each actual event record into one CSV row and merges entity/event metadata. Aggregational responses already contain row objects. In both cases columns are derived dynamically and values are CSV-escaped before download. No backend download endpoint is required.

Frontend CSV export contract

  • No backend download endpoint: CSV conversion is intentionally handled by the frontend.
  • No generated-data artifact: the backend does not create a JSON or CSV copy of the complete dataset on disk.
  • Transactional: the frontend can flatten each events[].records[] entry into one CSV row and retain event_type and other event metadata.
  • Aggregational: the frontend can export the generated records directly.
  • Dynamic columns: the frontend should derive columns from the actual generated records rather than using industry-specific hard-coded columns.
  • Edge cases: isEdgeCaseData remains part of the generated record and should be exported unchanged.
  • Filename: use proposed_scenario_id.csv when the frontend has the proposed scenario identifier from the scenario metadata.
Memory behavior: removing backend CSV persistence avoids creating a second full dataset representation on the server. The existing /scenario/generate API response contract is unchanged. The generator still retains the records required to construct that response; making generation itself constant-memory would require a separate batch/streaming redesign of the generator and QA pipeline.

Current Scenario API Lifecycle

flowchart TB P["POST /scenario/propose"] --> D["Draft
variables + edge cases + edgeCasePercentage"] I["POST /scenario/import-csv"] --> D D --> C["POST /scenario/confirm"] C --> V["Effective-schema validation
edge conditions + percentage 0..1"] V --> S["Confirmed scenario"] S --> G["POST /scenario/generate"] G --> EC["Generate normal + targeted edge-case records"] EC --> QA["Validate edge condition against actual values"] QA --> R["Generated JSON response"] R --> FE["Frontend display / CSV export"]

Why edge-case validation is part of the lifecycle: Edge cases enter through proposal or CSV import, can be edited during confirmation, and are checked against the effective schema before generation. During generation the requested percentage determines how many records are targeted, while the condition itself determines whether a record qualifies. QA then checks the actual generated values rather than trusting the boolean flag alone.
