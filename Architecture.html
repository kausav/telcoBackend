Ingenii Backend — Agentic Architecture Overview

1. Purpose

This service generates synthetic telecom "low-balance / top-up" event data for testing, analytics, and ML training pipelines. Instead of a fixed template, it uses a multi-agent pipeline (LLM + deterministic code) so that:

  • Business rules and validation logic are derived by an LLM from a plain-English scenario description (auditable, not hardcoded).
  • Bulk record generation itself is fast and deterministic (no LLM latency/cost per record).
  • New scenarios can be invented on demand by a human + LLM collaboration, without writing new generator code.

The 4 Pipeline Agents + 1 On-Demand Agent

3.1 Orchestrator Agent

Role: Gatekeeper — validates the scenario request before any generation work happens. Cheap sanity check, not a full workflow/state manager.

Inputs: scenario id, requested record count.
Outputs: pass/fail decision + execution notes; halts the pipeline immediately on failure.

  • Checks scenario exists (static config/scenarios.py + SQLite dynamic store)
  • Asks Gemini (temperature 0.1) to sanity-check the scenario and produce execution notes
  • Appends to state.errors and stops the pipeline on rejection

3.2 Rules Agent

Role: Derives the business rules and field constraints that generated records must satisfy — becomes the shared contract used later by QA.

Inputs: scenario metadata + variable definitions.
Outputs: business_rules[], field_constraints{}, cross_field_rules[] (temperature 0.1).

  • Summarizes every variable for the LLM
  • Produces a complete rules document covering all variables
  • Stores rules in shared state (state.rules) for the QA Agent to consume

3.3 Data Generator Agent

Role: The actual generation engine — zero LLM calls per record.

Inputs: variable catalog (static or dynamic) + scenario overrides.
Outputs: raw_records[].

  • Resolves each variable via a dispatch table (uniform, lognormal, beta, weighted_choice, formula, timestamp helpers, etc.)
  • Generates fields in dependency order so later fields can read earlier ones already written (e.g. account_id mirrors subscriber_id)
  • Sandboxes formula-type fields via eval() with __builtins__ disabled

3.4 QA & Validation Agent

Role: Two-layer validation — deterministic checks first, then LLM semantic audit.

Inputs: raw_records[], business rules from the Rules Agent.
Outputs: final_records[], validation_report{}.

  • Recomputes balance_after, trims to official field order, default-fills any null field (0 / "" / False)
  • Sends records in chunks of 50 to Gemini (temperature 0.1) for semantic review
  • Recovers any record the LLM drops (default-filled and re-added) so output count matches the request
  • Passes a chunk through unmodified (and logs an error) if its LLM call fails, rather than crashing the whole run

3.5 Agent 0 — Scenario Designer Agent (on-demand, not in main pipeline)

Role: Invents a brand-new scenario's full variable catalog from a plain-English business description, via /scenario/propose + /scenario/confirm.

Inputs: industryType, domain, businessScenario, optional businessResponse/expectedOutcome, plus feedback history.
Outputs: 15–35 variable catalog in the same generator vocabulary the Data Generator Agent already understands.

  • Normalizes field name synonyms to a canonical glossary (e.g. customer_id → subscriber_id)
  • Force-includes 3 mandatory cross-scenario fields
  • Retries once if too few variables are returned (temperature 0.3)
  • Persists confirmed scenarios into the SQLite store shared across all Cloud Run / uvicorn worker processes

4. Validation Approach (actual — no separate "Progressive Validation Gates")

The current codebase does not implement separate named validation gate components. Validation is folded into two places:

  • Design-time validation → Rules Agent (derives constraints before generation)
  • Post-generation validation → QA Agent (algorithmic checks + LLM semantic audit, in chunks of 50)

5. Deterministic + AI Validation (actual split)

6. Orchestration State Management

Instead of a Firestore-backed GenerationState, the real implementation uses a single in-memory Pydantic model (core/state.py) passed by reference through each agent call:

WorkflowState
├── scenario            (e.g. "LB-01")
├── count                (records requested)
├── batch_size           (QA chunk size, default 50)
├── rules                (populated by Rules Agent)
├── raw_records          (populated by Data Generator Agent)
├── final_records        (populated by QA Agent)
├── validation_report    (populated by QA Agent)
├── errors               (any agent can append; halts the pipeline)
└── field_order          (populated by Data Generator Agent)

Persistence model (actual): SQLite (WAL mode) — data/dynamic_scenarios.db (drafts / confirmed / feedback tables). No Firestore / BigQuery / Cloud Storage integration exists. WorkflowState itself is not persisted between runs.

7. Agent Routing Logic and Error Recovery (actual)

flowchart TB START["run_pipeline()"] --> O["Orchestrator"] O -->|state.errors set| STOP["Pipeline halts\n(for-loop break in main.py)"] O -->|ok| R["Rules Agent"] R --> G["Data Generator Agent"] G --> Q["QA Agent"] Q -->|chunk LLM call throws| PASS["Log error,\npass chunk through unmodified"] Q -->|success| FINAL["final_records +\nvalidation_report returned"]
  • Orchestrator rejection → pipeline stops immediately, no downstream agents run
  • QA per-chunk LLM failure → chunk is logged as an error and passed through as-is, not retried or routed back
  • No root-cause-classified routing back to Rules/Data Generator Agent on QA failure exists today

8. Deployment Topology (actual — GCP)

flowchart LR GH["GitHub push"] --> CI[".github/workflows/gcp-deploy.yml"] CI -->|build and push| AR["Artifact Registry<br/>telco-backend repo"] CI -->|deploy| CR["Cloud Run service<br/>listens on PORT"] SM["Secret Manager<br/>GEMINI_API_KEY"] -.->|injected at deploy| CR CR --> USERS["API consumers"]
  • Container listens on $PORT (Cloud Run convention, default 8080)
  • Gemini key injected from Secret Manager at deploy time — never baked into the image or committed
  • Known limitation: Cloud Run's filesystem is ephemeral and not shared across instances — the SQLite dynamic-scenario store does not persist reliably across revisions/scale-out there

9. Final Architecture Principles (actual, revised from aspirational doc)

  • Direct client input flow: CLI or API request feeds straight into run_pipeline() — no separate Domain Knowledge Layer
  • Generation does not wait on QA approval — generation and validation are sequential stages, not a gated loop
  • Deterministic generation, hybrid validation
  • No contract objects / versioning — WorkflowState is the only hand-off object, valid for one run
  • No forward/reverse traceability implementation exists today
  • Reproducibility is partial — no random seed capture or generation manifest is persisted

11. Future Work — Gaps vs. the Aspirational Design

# Aspirational concept Status today
1 Dedicated Edge Case Agent Not implemented. Edge cases are only whatever the Scenario Designer happens to encode.
2 LangGraph-based orchestration Not implemented. Plain sequential Python loop in main.py.
3 Firestore / BigQuery / Cloud Storage Not implemented. SQLite (WAL) is the only persistence layer.
4 Cloud Run Jobs / Dataflow generation engine Not implemented. Generation runs synchronously in the API/CLI process.
5 Progressive Validation Gates as separate stages with retry loop Not implemented as separate components; folded into Rules + QA agents.
6 Forward/reverse traceability Not implemented. No artifact versioning or lineage tracking.
7 Random seed capture / generation manifest Not implemented. Runs are not reproducible today.
8 Root-cause-classified error routing Not implemented. QA failures are logged and passed through, not routed back.

All request/response fields below are taken directly from the Pydantic models in server.py. "Required" means the field has no default (must be supplied); everything else is optional and falls back to its default (often null / empty list) if omitted or sent as blank/"string"/null placeholder text.

POST /scenario/propose — API 1

Purpose: Ask the Scenario Designer agent (LLM) to invent a brand-new scenario's variable catalog from a plain-English business description. Produces a draft that must be reviewed/finalized via /scenario/confirm.

Request body (ProposeRequest):

Field Type Required Description
scenarioId string Yes Preferred scenario id label, e.g. LB-04 (not reserved yet — collisions resolved at confirm time)
scenarioType string Yes e.g. Normal, No Response, Customer Declines
industryType string Yes e.g. Telecom
domain string Yes e.g. Low Balance & Top-up
businessScenario string Yes Plain-English description of the trigger scenario
businessResponse string No Expected business reaction to the scenario (default null)
expectedOutcome string No Expected end state (default null)
country string No ISO 3166-1 alpha-2 code; omit for generic/global conventions (default null)
useCase string No Sharper context than domain alone (default null)
typeOfData "transactional" | "aggregational" Yes Output data grain

Response body (ProposeResponse):

Field Type Description
draft_id string Unique handle for this draft; pass to /scenario/confirm
scenario_id string Echo of requested scenarioId
scenario_id_available bool false if that scenarioId is already confirmed under a different draft
label string Human-readable scenario label
journey string Journey/domain name
description string Generated scenario description
variables list[object] Proposed variable catalog (15–35 vars)
field_order list[string] Ordered variable names
typeOfData "transactional" | "aggregational" Echo of request
events list[object] Transactional event definitions (empty for aggregational)

POST /scenario/import-csv

Purpose: Alternative to API 1 — load an industry-supplied CSV variable catalog directly instead of having the LLM invent one. Produces a draft in the same shape as /scenario/propose, so it still goes through /scenario/confirm. Multipart form data, not JSON.

Request body (multipart form fields):

Field Type Required Description
file file (CSV) Yes Columns: name, dtype, gen, params, description, depends_on, nullable, formula
scenarioId string Yes Preferred scenario id label
domain string Yes Domain name
industryType string No Default "generic"
country string No Default null
businessScenario string No Default ""
scenarioType string No Default ""
label string No Default "" (falls back to scenarioId)

Response body: same shape as ProposeResponse above (typeOfData is always "aggregational" for CSV imports).

POST /scenario/confirm — API 2

Purpose: Apply user add/edit/delete changes (and optional feedback) to a draft, then finalize it into a usable scenario stored in SQLite.

Request body (ConfirmRequest):

Field Type Required Description
draft_id string Yes Draft handle returned by propose/import-csv
add list[object] No New variable definitions to add (default empty list); each needs a name key
edit list[{name, changes}] No Existing variables to edit by name (default empty list)
delete list[string] No Variable names to delete (default empty list)
eventAdd list[object] No Transactional events to add — transactional scenarios only (default empty list)
eventEdit list[{event_type, changes}] No Transactional events to edit by event_type (default empty list)
eventDelete list[string] No Transactional event_type values to delete (default empty list)
feedback string No Free-text feedback saved for future proposals (default null)

Blank/"string"/null placeholder values in any of the above (except draft_id) are treated as "no value" and skipped rather than applied literally.

Response body (ConfirmResponse):

Field Type Description
scenario_id string Final confirmed scenario id (may differ from requested if reassigned)
requested_scenario_id string The scenarioId originally requested at propose time
scenario_id_reassigned bool true if scenario_id was reassigned due to a collision
draft_id string Echo of request draft_id
label string Final scenario label
journey string Journey/domain name
description string Final scenario description
variables list[object] Final variable catalog after add/edit/delete
field_order list[string] Ordered variable names
typeOfData "transactional" | "aggregational" Data grain
events list[object] Final event definitions after eventAdd/eventEdit/eventDelete

POST /scenario/generate — API 4

Purpose: Run the 4-agent pipeline (Orchestrator → Rules → Generator → QA) for a confirmed scenario and return generated records.

Request body (GenerateRequest):

Field Type Required Description
scenario string No* Confirmed scenario id, e.g. LB-01 (default null)
draftId string No* Confirmed draft id; disambiguates when scenarioId collided across users (default null)
count integer No Number of records to generate, 1–5000 (default 20)

*Either scenario or draftId must be supplied (enforced at runtime, not by the schema) — a 400 is returned if both are missing.

Response body (GenerateResponse):

Field Type Description
scenario_id string Resolved scenario id used for generation
typeOfData "transactional" | "aggregational" Data grain
events list[object] Scenario's event definitions
requested_scenario_id string Originally requested scenarioId at propose time, if different from scenario_id
draft_id string Echo of request draftId, if supplied
scenario_label string Human-readable scenario label
fields list[string] Ordered field names
total_records integer Total number of generated records
validation_report object QA agent's validation summary
records list[object] Generated data — flat records for aggregational, entities grouped by entityKey (each with nested events) for transactional, latest 10 entities/events only
entityKey string Field used to group transactional records by business entity (null for aggregational)
totalCount integer Total unique entities (transactional) or records (aggregational)
eventData list[object] Deprecated/always empty; kept for backward compatibility
errors list[string] Any pipeline errors/warnings encountered

5. Frontend Data Export

The backend no longer exposes a CSV download API and does not persist generated datasets under a generated_data directory. The /scenario/generate response remains the source of the generated data, and the frontend is responsible for converting the received records into CSV when the user chooses to download them.

flowchart LR G["POST /scenario/generate"] --> R["Generated JSON response"] R --> T{"typeOfData"} T -->|transactional| TR["Flatten events.records"] T -->|aggregational| AR["Use records"] TR --> CSV["Frontend CSV export"] AR --> CSV CSV --> F["proposed_scenario_id.csv"]

Frontend CSV export contract

  • No backend download endpoint: CSV conversion is intentionally handled by the frontend.
  • No generated-data artifact: the backend does not create a JSON or CSV copy of the complete dataset on disk.
  • Transactional: the frontend can flatten each events[].records[] entry into one CSV row and retain event_type and other event metadata.
  • Aggregational: the frontend can export the generated records directly.
  • Dynamic columns: the frontend should derive columns from the actual generated records rather than using industry-specific hard-coded columns.
  • Edge cases: isEdgeCaseData remains part of the generated record and should be exported unchanged.
  • Filename: use proposed_scenario_id.csv when the frontend has the proposed scenario identifier from the scenario metadata.
Memory behavior: removing backend CSV persistence avoids creating a second full dataset representation on the server. The existing /scenario/generate API response contract is unchanged. The generator still retains the records required to construct that response; making generation itself constant-memory would require a separate batch/streaming redesign of the generator and QA pipeline.
