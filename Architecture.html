Synthetic Data Generator — Architecture

Deterministic, industry-agnostic synthetic data generation. The same service started as a telecom prepaid generator and now serves any industry (for example BFSI) through one agentic flow. Accuracy comes from LLM prompts grounded in industry_source_documents and in the variable definitions, not from per-industry rule packs.

1. Principles

  • Data, not code. The behaviour of a scenario is a GenerationSpec (engine event_rows/v1): plain JSON that an interpreter executes. An LLM may write the spec; it never writes executable code.
  • Determinism. The same seed and asOf date over the same spec give byte-identical rows. Randomness is derived from the seed, never from the clock.
  • Verified before served. A designed spec is simulated and checked by a simulator and by an independently written set of expectations before it is trusted.
  • One answer per call. The first /scenario/generate returns the same data as every later call. A request waits for the design to settle; it does not serve a draft and improve it afterwards.
  • Honest quality flags. If defects remain, the response says so (quality_target_met=false, open_findings) instead of claiming success.
  • Scenario type changes behaviour. scenarioType is part of the brief and of the spec key, so different types produce different specs and different data.
  • Root-cause fixes. No per-column or per-industry special cases. Industry knowledge enters through the source documents and the variable definitions.
  • Small configuration surface. Four environment variables (Gemini key, MongoDB URI and database name, API token); every other setting is a constant in config/constants.py.

2. Layers and components

API → workflow

Each route validates input and delegates. No business rule lives in server.py.

Workflow → synth

Propose and confirm decide which variables. Synth decides how the data behaves. The two meet at spec_key.

Synth → response

Rows come from the spec interpreter. The generation service wraps them with a validation report.

3. Sources of truth

Variable sources

  1. MongoDB scenario_variables — variables persisted for a requestedScenarioId (version 1 by default). Always consulted first.
  2. Industry JSON source (industry_source_documents) — a deduplicated catalogue of models and fields for an industry and domain. When present, propose runs the JSON-grounded path and the DB variables overlay it.
  3. CSV import — /scenario/import-csv turns a CSV of variable definitions into a scenario with the same contract as the other two.

Duplicates across sources are removed by variable key; the DB definition wins.

Propose with no JSON source. The variable set is exactly the persisted scenario_variables of the requested scenario id. The LLM acts only as a reviewer of that set; it cannot invent variables.
Generation gate. For confirmed agentic JSON-grounded scenarios every variable must carry a recognised source label or source id (live sources are not re-read, so a later source change cannot break a confirmed scenario). For other scenarios an active JSON source or persisted scenario variables must exist, otherwise HTTP 400. /scenario/propose with neither also returns HTTP 400.

CSV variable format

Columns: name, dtype, gen, params, depends_on, nullable, formula, description. params is a JSON object (for example {"choices":[true,false],"weights":[0.18,0.82]}); typed values such as booleans must go through JSON so they are not read as strings. Entity-scope variables come first, then event-scope variables.

5. Scenario lifecycle

Warm design

SPEC_WARM_ON_PROPOSE=true (default) starts the design in the background at propose, import-csv and confirm. pin_spec only names the spec (computes spec_key) without waiting; resolve_spec is the call that waits.

6. Variable definitions and the contract

A variable definition describes one column: name, dtype, generator kind (gen), parameters, dependencies, nullability, optional formula and description. variable_contract and definition_audit validate definitions; validate_db_definition rejects definitions whose typed parameters are wrong (for example string booleans).

  • Scope. entity variables are drawn once per entity (customer, account, loan); event variables are drawn per row (payment, call, transaction). Entity scope is listed first.
  • Dependencies. depends_on orders the draw so a column can read the columns it depends on.
  • Ordering rule. Database variables first, then JSON variables, deduplicated by key.
  • Contract. synth/contract.py carries the column rules (dtype, range, format, nullability) that both the baseline and the verifier enforce.

7. GenerationSpec and the row engine

The spec is the single description of behaviour. synth/baseline.py builds a baseline from the definitions; the compiler overlays an LLM-authored overlay using merge. The engine synth/engines/rows.py executes the merged spec.

Spec partMeaning
scopeEntity column, event column, row counts per entity.
clockEvent timeline anchored to asOf; event times never lie after asOf.
emitWhich columns appear and how each is produced (sampler, expression, derivation).
latentsHidden per-entity variables (risk, engagement) that several columns read, so related columns agree.
timeline / slow_stateState that evolves over events (balance, status) and changes slowly rather than flipping every row.
rollupsPer-entity aggregates over events (totals, counts, latest value).
invariantsHard rules every row must satisfy (for example amount ≤ limit).
targetsDistribution targets (share of a category, mean of a measure).
samplersSeeded draws: choices with weights, ranges, normal, lognormal, dates, ids, and pool (an id drawn from a pool that all entities of the run share: members = entities × ratio, so several entities point at one party).

Expression language (synth/expr.py)

A small, safe expression language: arithmetic, comparisons, boolean logic, conditionals, and a fixed function set (add_days, add_secs, int, float, sigmoid, abs, round, secs, days, hour_of, ...). It cannot call arbitrary code.

Null propagation. A binary or unary operation with an empty operand yields empty. An ordering comparison with empty is false. The date and numeric functions listed above return empty for empty input. This stops arithmetic on a legitimately empty value from crashing a design with NoneType + float.

Coverage attempts

_simulate_with_coverage runs a deterministic sequence of attempts derived from the seed, choosing the first attempt that has no empty or stuck column. Same seed, same choice.

8. Design pipeline

Independent expectations (synth/expectations.py)

A separate LLM call sees only the scenario brief and the column cards. It never sees the author's overlay, so it cannot grade its own homework. It answers in a closed vocabulary:

  • entity_facts, constants — things true of an entity or constant across its rows.
  • rules: present_iff, order, at_most, determined_by, holds, separate, slow_state.
  • state_shares — expected share of each state value.
  • trajectories — columns that must change over an entity's events because the scenario describes a progression.
  • shared_parties — columns that name another party the scenario says is shared between entities (a network); measured as the share of entities whose party another entity also has.

Findings from it have ids starting expected_. The result is cached by sha256(PROMPT_HASH + prompt) and stored in overlay["expectations"]. Guidance in its prompt: when two columns merely agree in direction (for example a rating and a score), state a band or an order relation, never an exact formula.

Measured advice (ids in MEASURED_FINDINGS) is computed on the simulated rows. Added in compiler 16–17:

IdMeasures

amount_tableA money-movement amount drawn from a short table (few distinct values, shared by three or more entities).
balance_not_runningA balance that does not change by the amount of the later event between consecutive events (or does not change at all).

Advisory advice never blocks. Examples: value polarity (a state named no_… or not_… must not behave like its opposite; negating words adjacent to the step are recognised) and in-flight advice, which skips columns whose tokens overlap the entity column's tokens.

Measured vs reviewer findings

  • Measured findings come from the simulator (ids in MEASURED_FINDINGS) or from expectations (ids expected_*). They are facts about generated rows.
  • Reviewer findings are an LLM's opinion on the spec text. They guide, but never overrule a measurement.

Acceptance rule (_accepts): a candidate patch is rejected if it raises the number of measured errors; otherwise it is accepted if measured weight falls (or, when requested, total weight falls). Good enough means weight ≤ GOOD_ENOUGH_WEIGHT=1.

Repair, quarantine and refinement

  1. Draft. Author call, merge, verify. Structural problems are retried; soft problems go to quarantine as soon as the next round would not fit the window.
  2. Repair. _repair_measured asks the author for a patch that targets measured problems only (up to MAX_REPAIR_ROUNDS=2), accepted only through the acceptance rule.
  3. Quarantine (_heal_soft). A defect is confined to one column instead of discarding the design. Notes healed_* are stored in overlay["healed"] and surfaced as confined_defects.
  4. Refine. A reviewer reads the spec, then patch rounds (up to MAX_REFINE_ROUNDS=6, rejected patches allowed REJECTED_PATCH_ALLOWANCE=2) run only while a round fits the window. The reviewer is skipped when no round could fit.

Design window and cost model

The design has an expected duration, SPEC_DESIGN_SECONDS (default 720), counted from design start. A further round is started only if it is expected to finish inside that window:

expected = max(author_seconds_seen, first_author_seconds, PATCH_SECONDS=45)
           + (REVIEW_SECONDS=20  if a reviewer read is included)
fits     = spent + expected <= window

Draft rounds after the first and the inline repair use the same test. When the window is spent, soft problems are healed by quarantine and the design stops, so the call returns a settled spec instead of overrunning.

Bounds on the first design. Three limits keep the first design from running long. (1) Repair rounds before the first serve run only inside SPEC_FIRST_SERVE_SECONDS (420). (2) Every model call of the first design — author, expectations, repair, draft review — gets a deadline at SPEC_DRAFT_HARD_SECONDS (480): a call is given only the time that is left (its timeout is cut to fit), none is begun with less than 15 s left, and retries stop at the deadline. A review that ran beside an unchanged spec is waited for only until that deadline. (3) A first design that cannot be completed in time is reported as unavailable; generation then serves the definitions-only fallback (quality_target_met=false) and the design is retried shortly afterwards. A first spec with no open error is served at once (SPEC_SERVE_EARLY) while refinement continues; one with open errors is refined for at most SPEC_SETTLE_SECONDS (180) before it is served.

Trade-off. Raising SPEC_DRAFT_HARD_SECONDS or SPEC_FIRST_SERVE_SECONDS buys accuracy at the price of a longer first call.

Settle semantics (synth/service.py)

  • A spec is settled when it is reviewed, or when its refinement ended because the window ran out (refinement.stopped == "time").
  • _after_refinement returns a reviewed spec at once; otherwise it waits while the key is being refined or scheduled, up to what is left of the request's wait, then reads the stored spec.
  • Backoff for a skipped or deferred review is set only when the refinement is not settled.

9. Latency model

StageWhere the time goesNotes
Propose / confirmVariable resolution; design starts in background.Do not wait for the design.
DesignLLM calls (author, patch, review). Expectations run in parallel.Bounded by SPEC_DESIGN_SECONDS.
Generate (spec ready)Row engine plus validation.200 rows well under 1 s; repeat calls about 0.7 s (observed).
Generate (spec in flight)Waits for the design to settle.Up to SPEC_GENERATE_WAIT_SECONDS (20).
  • Latency is dominated by model calls, not by generation.
  • The expectations call overlaps the first author call, so it adds nothing to wall-clock time.
  • If the wait elapses while the design is still in flight, generate returns SpecNotReady as HTTP 503 with a Retry-After header.
  • Observed timings come from real Gemini runs made by the project owner (gemini-3.8-flash). They are observations, not guarantees.
Because a first call can run past 90 s on a slow model, a gateway in front of the service should allow at least SPEC_GENERATE_WAIT_SECONDS, or the design window and wait should be lowered together.

10. Determinism and caching

  • Spec key. spec_key = sha256 of [COMPILER_VERSION, SPEC_VERSION, hash(SYSTEM_PROMPT), expectations PROMPT_HASH] plus the brief keys and the sorted column definitions. Change any of them and the design is redone; leave them and the stored spec is reused.
  • COMPILER_VERSION is currently 9. It must be raised when design behaviour changes in a way that should invalidate stored specs.
  • Pinning. Confirmation stores the spec key on the scenario, so later calls read the same spec even if prompts change.
  • Store (synth/store.py). MongoDB generation_specs plus a process cache: CACHE_SECONDS=60, FAILURE_TTL_SECONDS=300, TRANSIENT_FAILURE_TTL_SECONDS=30. Specs carry a revision that increases on every accepted improvement.
  • Rows. Same spec, seed and asOf ⇒ same rows. The clock is the asOf date, never the wall clock.
  • Expectations cache. Keyed by prompt hash, so an unchanged scenario never re-asks.

14. Limits

  • The scorer measures internal consistency of the generated data against the spec, the contract and the independent expectations. It does not measure calibration against real-world data.
  • Accuracy depends on the quality of the industry source documents and the variable definitions supplied.
  • Timings depend on the model and on load; the numbers in this document are observations.
  • Development testing used stand-in models (Sonnet sub-agents and scripts), not real Gemini. Behaviour with real Gemini replies has to be confirmed in the target environment.
  • A short design window favours latency over accuracy; some designs will finish with confined defects or open errors, which the response reports.
